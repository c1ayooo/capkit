# 工具调用协议

capkit 的工具调用只有**一个形状**：给一个工具名 + JSON 输入，拿回一个固定信封。agent、宿主 BFF、前端、CLI 说的是同一套话，谁都不要自己发明返回结构。

契约的机器可读版本在 [`contracts/`](../contracts/)：`output.json`（信封不变量）、`result.json`、`tool.json`、`target.json`、`evidence.json`。本文是给人看的同义版。

## 1. 三方角色

```
调用方（agent / 前端 / CLI）
   │  ① 发现：GET /tools  → 工具名 + input_schema + output_schema + risk
   │  ② 调用：POST /call   {tool, input, context}
   ▼
宿主 BFF（鉴权、项目归属、trace）
   ▼
capkit runtime（门禁 → kit → finalize）
   │  ③ 返回：{result: <信封>}
   ▼
调用方按 result.status 决策
```

调用方永远不需要知道是哪个 kit 在干活 —— `meta.tool` 就够了。

## 2. 发现：先拿 schema，再调用

```
GET /api/capkit/tools
→ {"tools": [ToolSpec, ...]}
```

```jsonc
{
  "name": "inet_portscan",
  "description": "从会话出发对给定主机/网段做 TCP 端口扫描……",
  "input_schema":  { "type": "object", "properties": { ... }, "required": [...] },
  "output_schema": { "type": "object", "properties": { ... } },
  "risk": "medium",                                   // low | medium | high
  "rate_limit": { "per_second": 1, "burst": 1, "concurrency": 2 }
}
```

规则：

- `input_schema` 是**调用前**的唯一真相，`output_schema` 约束 `result.data`。两者都非空且合法，CI 已强制。
- `risk` 决定宿主是否需要人工确认（默认 `high` 起）。前端应当在 high 工具上出确认弹窗。
- `ExtractTargets` 是 Go 函数（不外传）：runtime 用它从输入里抠出目标去过 scope。**输入里写了目标就会被校验**，不管是哪个字段。
- `GET /api/capkit/manifests` 返回能力级信息（版本、`requires` 端口、settings、events），用于宿主的自检页和运维视图。

## 3. 调用

```
POST /api/capkit/call
Content-Type: application/json

{
  "tool": "http_probe",
  "input": { "url": "https://example.com/" },
  "context": { "project_id": 7, "task_id": "recon-1", "actor": "alice", "dry_run": false }
}
```

响应（**永远 HTTP 200**）：

```json
{ "result": { ...信封... }, "error": "scope_denied: 目标不在授权范围" }
```

`error` 只是给人看的字符串镜像，机器判断一律用 `result.status` / `result.error.code`。即使 `error` 非空，`result` 也是完整信封。

### `context` 字段

| 字段 | 含义 | 谁填 |
|---|---|---|
| `trace_id` | 贯穿门禁、审计、证据的链路 id | 宿主（缺省自动补） |
| `project_id` | 项目归属，scope 校验和证据落库都靠它 | 宿主（**必须覆盖客户端值**） |
| `task_id` | 同一任务内幂等/审计分组；重试换它就绕开缓存 | 调用方 |
| `actor` | 操作人 | 宿主 |
| `dry_run` | 只规划不落地的提示位。目前没有 kit 分支于它，属**预留**字段：宿主/KIT 需要「预览态」时自行遵守 | 调用方 |

## 4. 信封

```jsonc
{
  "ok": true,
  "status": "success",
  "summary": "目标 /api/exec 存在命令注入，已用 id 命令确认回显，payload 为 ;id",
  "data": { ... },              // ≤8KB，受该工具 output_schema 约束
  "findings": [ ... ],          // 归一化结论，跨工具可去重
  "evidence": [ ... ],          // 只放引用，绝不放正文
  "next": [ ... ],              // 建议的下一步
  "truncated": false,
  "page":       { "total": 250, "cursor": "off:100", "has_more": true },
  "error":      { "code": "...", "message": "...", "retryable": false, "hint": "..." },
  "meta": {
    "tool": "cmdi_probe", "version": "0.4.0", "duration_ms": 842,
    "requests": 7, "target": "example.com", "cached": false,
    "gate_trace": ["scope:1ms", "ratelimit:0ms", "audit:2ms"]
  }
}
```

四个字段是硬性的，任何时候都在：`status`、`summary`、`error`（可为 null）、`meta`。

| 字段 | 读法 |
|---|---|
| `ok` | `status ∈ {success, partial}` 的快捷位，别用它替代 `status` |
| `status` | 六态，决定调用方下一步动作（见 §5） |
| `summary` | ≤200 字，可直接念给用户/喂给 LLM |
| `data` | 结构化载荷；结构由该工具的 `output_schema` 规定 |
| `findings` | 漏洞结论（见 §9） |
| `evidence` | 证据引用（见 §7） |
| `next` | 下一步候选（见 §10） |
| `truncated` / `page` | 截断与分页（见 §8） |
| `error` | 错误原子（见 §6） |
| `meta` | `tool`/`version`/`duration_ms`(>0)/`requests`/`target`/`gate_trace`/`cached` |

## 5. `status` 六态 —— 调用方的决策表

| status | 含义 | 调用方应当做什么 | 前端显示 |
|---|---|---|---|
| `success` | 完成，无风险 | 读 `data`/`findings` | 绿色成功 |
| `partial` | 部分完成（10 个目标里 2 个超时）或还在后台跑 | 读 `data`；若带 `job_id` 就轮询；若 `page.has_more` 就续取 | 黄色，提示「部分完成」 |
| `failed` | 失败 | 看 `error.retryable`：true 才重试，且按 `retry_after_ms` 退避 | 红色，带重试按钮 |
| `blocked` | 被门禁拦下（scope/approval/ratelimit） | **不要重试**；换目标、申请授权或降速 | 灰色锁，显示原因 |
| `need_human` | 高危动作等人工确认 | 挂起等确认，别重试 | 橙色，带「确认执行」 |
| `unavailable` | 依赖缺失（nuclei 未装、凭据未配） | 报告环境问题，别重试 | 灰色，显示缺失项 |

把六态压成 `ok=false` 会让 agent 一律重试 —— 撞在 scope 上死循环。这是六态存在的理由。

## 6. `error` 与固定 code 枚举

```jsonc
{ "code": "bad_input", "message": "inject_point.url 缺少 {{inject}} 占位符",
  "retryable": false, "retry_after_ms": 0,
  "hint": "在 url 里用 {{inject}} 标出注入点，例如 https://x/?q={{inject}}",
  "detail": "…给开发者，不要喂给 LLM…" }
```

| code | Retryable | 触发场景 | 调用方动作 |
|---|---|---|---|
| `scope_denied` | **false** | 目标不在项目授权范围 | 换目标或扩范围 |
| `approval_required` | false | 需要人工确认 | 走审批流 |
| `rate_limited` | true | 命中 per-host 限速 | 按 `retry_after_ms` 退避 |
| `target_unreachable` | true | 连不上 | 确认可达性后重试 |
| `timeout` | true | 超时 | 缩短范围/加超时后重试 |
| `tool_missing` | false | 会话不支持该能力 / 二进制没装 | 换会话或装依赖 |
| `bad_input` | false | 输入不合法（看 `hint`） | **按 hint 改参数**，别原样重试 |
| `upstream_error` | true | 上游/子进程报错 | 可重试 |
| `evidence_write_failed` | false | 证据落库失败 | 修存储 |
| `internal` | false | 内部错误 | 报 bug |
| `not_found` | false | 工具名/会话/任务 id 不存在 | 核对 id |
| `conflict` | false | 预览与确认不一致（如 cleanup 的 plan_id 变了） | 重新预览再确认 |
| `unavailable` | true | 依赖未就绪 | 修配置 |
| `need_human` | false | 与 `need_human` 状态对应 | 走审批 |

`hint` 存在时**优先渲染它**：这是参数该怎么改的直接答案。

## 7. 证据：只给引用，不给正文

```jsonc
"evidence": [{
  "id": "ev_7f3a", "kind": "http_exchange",   // http_exchange | file | command_output | scan_log
  "size": 1820, "sha256": "9f2c…", "preview": "HTTP/1.1 200 OK…<=200 字"
}]
```

- 响应体、文件内容、命令输出、扫描日志**一律不进 `data`**，只进证据库；`data` 里只有 id/大小/哈希/预览。
- `id` 非空 = 已落库，前端可以点开原文（宿主的 `/api/capkit/evidence/{id}`）。
- `id` 为空但有 `sha256`/`size` = 宿主没接 `EvidenceSink`，正文不可取（此时 `preview` 仍可用）。
- 因此「正文被截断」不是问题：`data` 的 8KB 上限管的是**摘要视图**，原文始终在证据库里。

## 8. 截断与分页

- `data` 单次上限 8KB。超了：`data` 被换成 `{"_truncated":true,"original_bytes":N,"preview":"…前 4KB…"}`，`truncated=true`，`page.total` 给出**真实原始字节数**（若工具自己已经按条数设过 `page.total`，则保留工具的值 —— 列表的总数是条数，不是字节）。
- 列表类工具（端口、命中、URL）超过 100 条必须分页：

```jsonc
// 第 1 次
{ "input": { ..., "page_size": 100 } }
→ "data": { "open": [ ... ], "open_count": 100, "total_open": 250 },
  "page": { "total": 250, "has_more": true, "cursor": "off:100" }

// 续取：把 cursor 原样回填，别自己拼
{ "input": { ..., "cursor": "off:100" } }
→ "page": { "total": 250, "has_more": false }
```

- `total` 是**全量真实条数**，不是本页条数；本页条数在 `data` 自己的字段里（端口扫描是 `data.open_count`，具体字段看该工具的 `output_schema`）。
- 游标非法（拼错/过期）返回 `bad_input`，不会静默回到第一页 —— 静默重置会让 agent 死循环拉第一页。
- 支持 `cursor` 的工具：`inet_portscan`、`github_secret_search`；其余工具的列表当前有界，只置 `truncated`。

## 9. `findings`：跨工具去重的漏洞结论

```jsonc
"findings": [{
  "target": "https://example.com/api/exec",
  "kind": "cmdi",
  "fingerprint": "cmdi|example.com|/api/exec|cmd",
  "confirmed": true,
  "payload": ";id",
  "evidence": ["ev_7f3a"],
  "source": "exploitkit"
}]
```

- `confirmed=false` 表示「有迹象未证实」，前端不要渲染成漏洞。
- `fingerprint` = `kind + host + path + payload token`，用于把 nuclei、exploitkit、模板命中合并成一条；前端按它去重，`source` 可能来自多个工具。
- `kind` 约定：`cmdi | sqli | ssti | lfi | ssrf | upload | deser | …`。

## 10. `next`：让调用方知道「还能做什么」

```jsonc
"next": [{
  "tool": "cmdi_execute", "reason": "已验证注入，可执行任意命令",
  "risk": "high", "preconditions": ["finding.confirmed"],
  "params": { "point": { "url": "…", "param": "q" }, "command": "id" }
}]
```

前端直接把 `next` 渲染成按钮：`params` 已经是可以回填的输入（可能仍需用户补全），`risk` 决定按钮是否需要二次确认。**不要**把 `next` 当成必须执行的指令 —— 它只是候选。

## 11. 幂等：重试不会打第二遍

- 幂等键由 **工具名 + 项目 + 执行者 + 任务 + 输入哈希** 生成，默认窗口 5 分钟。
- 窗口内重复调用直接返回上次结果，并置 `meta.cached=true`。此时 `meta.requests` 保留的是**首次**的消耗。
- **不缓存**：`blocked`/`need_human`/`unavailable` —— 授权变了、确认了、装好依赖了，重试必须真跑。
- 调用方想强制重跑：换 `task_id`。想关缓存：宿主调小/关闭 `IdempotencyWindow`。

## 12. 长任务：`async` + `job_status`

任何工具输入加 `"async": true` 即转后台（门禁仍在**同步**阶段跑完，所以 scope 被拦是立刻返回，不是轮询才发现）：

```jsonc
// ① 发起
{ "input": { ..., "async": true } }
→ { "status": "partial", "data": { "job_id": "job-1-…", "poll_after_ms": 2000, "tool": "nuclei_scan" },
    "next": [{ "tool": "job_status", "params": { "job_id": "job-1-…" } }] }

// ② 轮询
{ "tool": "job_status", "input": { "job_id": "job-1-…" } }
→ 运行中: { "status": "partial", "data": { "job_id": "…", "state": "running", "elapsed_ms": 12000, "poll_after_ms": 2000 } }
→ 已完成: 该工具自己的完整信封（status/data/findings/error 都是真实结果，meta.tool 仍是原工具）

// ③ 任务不存在或过期（默认保留 15 分钟）
→ { "status": "failed", "error": { "code": "not_found" } }
```

轮询建议：按 `poll_after_ms` 退避，别写 100ms 死循环；`status != partial` 即为终态。

## 13. 完整示例：一次命令注入探测

```jsonc
POST /api/capkit/call
{ "tool": "cmdi_probe",
  "input": { "point": { "url": "https://example.com/api/exec?q={{inject}}", "param": "q", "value": "1" } },
  "context": { "project_id": 7, "task_id": "web-1", "actor": "alice" } }
```

```jsonc
{ "result": {
    "ok": true, "status": "success",
    "summary": "命令注入已确认（technique=echo-time）：/api/exec 回显了唯一标记",
    "data": { "vulnerable": true, "payload": ";id", "technique": "echo-time", "probes": [ ... ] },
    "findings": [{ "kind": "cmdi", "fingerprint": "cmdi|example.com|/api/exec|cmd",
                   "confirmed": true, "payload": ";id", "source": "exploitkit" }],
    "evidence": [{ "id": "ev_7f3a", "kind": "http_exchange", "size": 1820, "sha256": "…" }],
    "next": [{ "tool": "cmdi_execute", "reason": "已验证注入，可执行任意命令", "risk": "high" }],
    "meta": { "tool": "cmdi_probe", "version": "0.4.0", "duration_ms": 842, "requests": 7,
              "target": "example.com", "gate_trace": ["scope:1ms", "approval:0ms", "ratelimit:0ms", "audit:2ms"] }
} }
```

调用方读完这一份就知道：成了、什么漏洞、证据在 `ev_7f3a`、能接着做什么、花了 7 次请求、各门禁耗了多少。

## 14. 兼容规则

- `status`/`summary`/`error`/`meta` 永远存在；新字段只增不改，消费者必须忽略未知字段。
- `data` 的形状由各工具的 `output_schema` 负责，改形状 = 改 schema + 提版本。
- `error.code` 是固定枚举，**不允许自由文本**；新增 code 属于破坏性变更，需要同步 `contracts/output.json`。
- `Result.Text` / `Result.EvidenceIDs` 是兼容旧宿主的遗留字段，新代码不要依赖。
