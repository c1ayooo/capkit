# 前端展示设计方案

> 状态：**设计方案，尚未实现**。接口、路由、组件按宿主仓库（4zrec）的现有约定给出（Next.js App Router + shadcn/ui + `web/src/lib/api.ts`），落地时照此编写。
>
> 本文所有 `web/…`、`internal/platform/server/…` 路径都在**宿主仓库**里，不在 capkit 模块内。

目标：一套**由 schema 驱动**的能力台。新增一个 capkit 工具时前端零改动 —— 表单从 `input_schema` 生成，结果按信封统一渲染。

## 1. 两条设计原则

1. **信封是唯一的渲染输入。** 不做「每个工具一个展示组件」。任何工具的返回都按 §6 的映射表渲染；工具特有的内容在 `data` 里，用它的 `output_schema` 描述，交给通用 JSON 树组件。
2. **表单由 schema 生成。** `input_schema` 已有的信息（类型、枚举、必填、描述）不再手写一遍。仓库已有先例：`web/src/app/(main)/system/tools/page.tsx` 的 `ParamRow` / `toRows` / `applyRows` 就是把 `schema.properties` 摊平成表单行，直接沿用这套思路。

## 2. 先看清楚：哪些已经有了

前端已经有一批结果消费页，**不要重复造**：

| 现有页面 | 现用途 | 与 capkit 的关系 |
|---|---|---|
| `/function/findings`（发现） | 漏洞库：复测、利用链、加深、导出、资产树、分组 | capkit 的 `Result.Findings` 由宿主**写入这里**；`fingerprint` 是去重键 |
| `/function/traffic`（流量） | 流量/证据库，选中记录用 Sheet 懒加载原文（`api.trafficExchange(id)`） | `EvidenceRef.id`（`http_exchange`）应深链到这里 |
| `/function/commands`（工具执行） | 工具执行记录表 + 详情 Sheet（`toolInput()` 渲染入参） | capkit 每次调用的落库记录应出现在这里（用 `trace_id` 串联） |
| `/function/connections`（连接管理） | 连接 CRUD + `connSSHExec` + SSH 终端对话框（xterm） | capkit 的 `session_*` 目标会话应复用这套控制台 |
| `/system/tools`（工具） | **自定义工具管理**（`createCustomTool`/`saveTool`/`testCustomTool`） | 注意：这是「用户自定义工具」，与 capkit 能力台不是一回事 |

所以本次**只新增两个页面**：能力台（工具目录 + 执行）和后台任务（异步 Job）。其余四个能力都是「把 capkit 的结果送进已有页面」。

## 4. 路由

沿用仓库约定：kebab-case 段、`page.tsx` 默认导出；**详情用静态段 + 查询参数**（`?id=`），不用动态段，并包在 `<Suspense>` 里（保证静态导出可用，参见 `function/tasks/detail/page.tsx`）。

| 路由 | 状态 | 说明 |
|---|---|---|
| `/function/capkit/tools` | **新增** | 左：工具目录；右：schema 表单 + 结果信封 |
| `/function/capkit/tools/detail` | **新增** | `?tool=inet_portscan`：完整 input/output schema、风险、限速、最近调用 |
| `/function/capkit/jobs` | **新增** | 后台任务列表；`?id=job-…` 查看终态信封 |
| `/function/findings/detail` | 已有 | 能力台产出的发现从这里下钻 |
| `/function/traffic` | 已有（小改） | 加 `?exchange=<id>` 支持，供证据引用深链 |
| `/function/connections` | 已有 | 会话控制台复用；capkit 只是多几种 `kind` |
| `/function/commands` | 已有 | 调用记录；按 `trace_id` 关联一次 capkit 调用 |

## 5. 宿主 BFF 接口

前端只调宿主自己的 `/api/...`（`web/src/lib/api.ts` 的 `http<T>()` 自动带 token、401 跳登录），不直连 capkit：

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| GET | `/api/capkit/tools` | — | `{ tools: ToolSpec[] }` |
| GET | `/api/capkit/manifests` | — | `{ manifests: Manifest[] }` |
| POST | `/api/capkit/call` | `{ tool, input, context }` | `{ result: CapToolResult, error?: string }` |
| GET | `/api/capkit/jobs/{id}` | — | `{ result: CapToolResult }`（内部转 `job_status`） |

证据原文与发现列表不新增接口 —— 直接用已有的 `/api/traffic/...` 与 `/api/findings/...`（`evidence.id` 就是流量记录 id 或证据库 id，取决于宿主的 `EvidenceSink` 实现，接线时对齐即可）。

后端按 `server.go` 的既有写法注册（Go 1.22 method 模式 + `writeJSON`/`writeErr`），鉴权走 `requireAuth` + `APIScope`，`project_id` 由服务端覆盖：

```go
mux.HandleFunc("GET /api/capkit/tools",     s.pgCapkitTools)
mux.HandleFunc("GET /api/capkit/manifests", s.pgCapkitManifests)
mux.HandleFunc("POST /api/capkit/call",     s.pgCapkitCall)
mux.HandleFunc("GET /api/capkit/jobs/{id}", s.pgCapkitJob)
```

**始终 HTTP 200 + `{result}`**，包括门禁拦截；让前端按 `result.status` 分支，否则拿不到 `error.hint`。handler 命名沿用 `pgListTools` / `pgTestCustomTool` 的 `pg` 前缀风格。

### 前端 API client（`web/src/lib/api.ts` 内追加）

`http` / `get` / `post` / `arr` 都是该文件内的模块私有 helper，新方法写在同一个文件里即可：

```ts
export const capkitApi = {
  tools:     ()           => get<{ tools: CapToolSpec[] }>("/capkit/tools").then((r) => arr(r.tools)),
  manifests: ()           => get<{ manifests: CapManifest[] }>("/capkit/manifests").then((r) => arr(r.manifests)),
  call:      (body: CapCallRequest) => post<{ result: CapToolResult; error?: string }>("/capkit/call", body),
  job:       (id: string) => get<{ result: CapToolResult }>(`/capkit/jobs/${encodeURIComponent(id)}`),
};
```

也可以挂在现有 `api` 对象上（`api.capkitTools()` 之类），与 `api.tools()` 并列，风格上更统一。

### 类型（放 `web/src/lib/types.ts`，PascalCase + snake_case 对齐后端 JSON）

```ts
export type CapStatus = "success" | "partial" | "failed" | "blocked" | "need_human" | "unavailable";
export type CapRisk   = "low" | "medium" | "high";

export interface CapToolSpec {
  name: string; description: string;
  input_schema: Record<string, unknown>;
  output_schema?: Record<string, unknown>;
  risk: CapRisk;
  rate_limit?: { per_second?: number; burst?: number; concurrency?: number };
}

export interface CapToolError {
  code: string; message: string; retryable?: boolean;
  retry_after_ms?: number; hint?: string; detail?: string;
}

export interface CapFinding {
  target: string; kind: string; fingerprint?: string;
  confirmed: boolean; payload?: string; evidence?: string[]; source?: string;
}

export interface CapEvidenceRef {
  id: string; kind: "http_exchange" | "file" | "command_output" | "scan_log";
  size: number; sha256?: string; preview?: string;
}

export interface CapNextStep { tool: string; reason: string; preconditions?: string[]; risk?: CapRisk; params?: unknown }

export interface CapPage { total: number; cursor?: string; has_more: boolean }

export interface CapMeta {
  tool: string; version?: string; duration_ms: number; requests?: number;
  target?: string; gate_trace?: string[]; cached?: boolean;
}

export interface CapToolResult {
  ok: boolean; status: CapStatus; summary: string;
  data?: unknown; findings?: CapFinding[]; evidence?: CapEvidenceRef[]; next?: CapNextStep[];
  truncated?: boolean; page?: CapPage; error?: CapToolError; meta: CapMeta;
}

export interface CapCallRequest {
  tool: string; input: unknown;
  context?: { project_id?: number; task_id?: string; actor?: string; dry_run?: boolean };
}

export interface CapSessionInfo {
  id: string; kind: string; host?: string; port?: number; user?: string;
  os?: string; arch?: string; elevated?: boolean; labels?: string[];
}
```

## 6. 信封 → 界面 映射（核心）

### 6.1 `status` 决定整块结果区的形态

| status | 徽章 | 颜色 | 主区内容 | 操作 |
|---|---|---|---|---|
| `success` | 成功 | 绿 | `data` + `findings` | 「查看证据」「执行下一步」 |
| `partial` | 部分完成 | 黄 | `data` + 未完成原因 | 有 `job_id` → 转任务卡片；`page.has_more` → 「加载更多」 |
| `failed` | 失败 | 红 | `error.message` | 只有 `retryable` 才显示「重试」，并按 `retry_after_ms` 倒计时 |
| `blocked` | 已拦截 | 灰 + 锁 | `error.message`（如「目标不在授权范围」） | **不显示重试**；显示「去申请授权」 |
| `need_human` | 待确认 | 橙 | `error.message` + 工具/目标/风险 | 「确认执行」（走宿主审批流） |
| `unavailable` | 依赖缺失 | 灰 | 缺失项（如「nuclei 未安装」） | 「查看环境自检」 |

把六态压成 `ok=false` 会让用户/agent 一律重试 —— 撞在 scope 上死循环。

### 6.2 其余字段

| 字段 | 展示 |
|---|---|
| `summary` | 结果区标题，最多两行 |
| `data` | 通用 JSON 树（复用 `components/http-code-block.tsx` 的 `JsonBody`）；若目录里有 `output_schema`，先按 schema 渲染已知字段，其余折叠进「原始 JSON」 |
| `findings[]` | 卡片：`kind` 标签、`confirmed` 决定「已确认/疑似」、`payload` 等宽字体、`source` 浅色 chip；`fingerprint` 相同则合并并并列多个 `source` |
| `evidence[]` | 一行一个：`kind` 图标 + `size` + `sha256` 前 8 位 + `preview`；`id` 非空 → 点击跳 `/function/traffic?exchange=<id>`（`http_exchange`）或对应证据页；`id` 为空 → 显示「未接入证据库」并禁用点击 |
| `next[]` | 按钮组；`risk: high` 用危险色并二次确认；点击用 `params` 回填表单并切到目标工具 |
| `page.has_more` | 列表底部「加载更多」，把 `page.cursor` 原样回填 |
| `truncated` | 顶部提示条：「内容已截断，共 `page.total` 字节，完整内容见证据」 |
| `meta.requests` | 页脚：`7 次请求 · 842ms`，让使用者对请求预算有感知 |
| `meta.cached` | 「命中缓存」chip，避免误以为刚刚真跑了一遍 |
| `meta.gate_trace` | 折叠区「为什么这么慢」：`scope:1ms / ratelimit:0ms / audit:2ms` |
| `error.hint` | 紧贴参数表单显示（红色），这是改参数的直接答案 |

表单细节：

- 必填项来自 `schema.required`，标 `*`；`description` 作 placeholder 或字段下方小字。
- `risk: high`：执行按钮用危险色，点击先出确认弹窗（显示工具名、从输入里提取的目标、风险级别）。
- `dry_run` 开关 → 请求 `context.dry_run = true`。
- 「异步」勾选 → 请求加 `async: true`，结果区切成任务卡片（§8）。
- 前端先按 schema 做 required/type/enum 校验，减少 `bad_input` 往返；服务端仍是权威。

## 8. 后台任务页

`/function/capkit/jobs`：表格（`components/ui/table.tsx` + `components/table-pagination.tsx`），列 = 任务 id（截断）、工具、状态、开始时间、已耗时、操作。

- 运行中：行内 `ui/spinner.tsx` + 已耗时递增；按 `poll_after_ms` 轮询（别写 100ms 死循环）。
- 完成：状态列换成终态 `status` 徽章；点开 `?id=job-…` 直接渲染该工具的真实信封 —— 注意 `meta.tool` 是**原工具名**（不是 `job_status`），列表要显示原工具。
- 过期（`not_found`）：显示「已完成但超出保留窗口」，提供「重新执行」。

## 9. 与已有页面的衔接

三条连接键，写进方案里就能打通，不需要新页面：

| 连接键 | 从哪里来 | 到哪里去 |
|---|---|---|
| `trace_id` | `CapCallContext.TraceID`（宿主生成） | `/function/commands` 的执行记录；`meta.gate_trace` 解释慢在哪 |
| `evidence[].id` | `EvidenceSink.Record` 的返回 | `/function/traffic?exchange=<id>` 看原文（需给流量页加这个查询参数） |
| `findings[].fingerprint` | 工具产出 | `/function/findings` 的既有去重/利用链/复测流程 |

会话：`session_open/exec/close` 在能力台里就是普通工具；`/function/connections` 只需把 `kind` 扩到 `ssh|winrm|smb|cli|webshell` 并复用其 SSH 终端对话框（`function/connections/_components/ssh-terminal-dialog.tsx`）渲染 `session_exec` 的输出。

## 10. 状态与异常

- **加载**：`components/ui/skeleton.tsx` 骨架屏（结果区、表格）。
- **空**：`components/ui/empty.tsx` + 一句引导。
- **错误**：网络/500 → `sonner` toast；**工具错误不弹 toast**，按 §6.1 渲染在结果区（用户需要看到 `hint` 和重试按钮）。
- **权限**：`http()` 已处理 401；未授权项目 → 页面级 empty 提示。
- **危险操作**：`cleanup_apply`、`persist_apply`、`lat_*`、`session_*` 一律二次确认，且结果区保留「谁在何时确认」。

## 12. 几条不要做的事

- 不要按 `ok` 布尔分支渲染 —— 六态的 UI 动作完全不同（§6.1）。
- 不要把 `data` 当正文来源；正文在证据库，`data` 只是摘要视图。
- 不要把 `confirmed: false` 的 `findings` 渲染成漏洞。
- 不要自己拼 `cursor` 或 `project_id`：`cursor` 原样回填，`project_id` 由服务端定。
- 不要重复实现发现/流量/连接/执行记录页面 —— 这四个已经有了，把 capkit 的结果送进去即可。
- 不要为单个工具写死展示组件；优先用 `output_schema` 驱动的通用渲染。
